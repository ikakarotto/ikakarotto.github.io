第一部分：三者核心定位

1.1 Spec-Kit（GitHub 官方）

规范驱动开发（SDD）流程工具。 核心逻辑是把"写规格"当成主要工作，代码是规格的产物。

  • 提供一整套线性流程：/speckit.constitution（项目原则）→ /speckit.specify（需求规格）→ /speckit.clarify（澄清）→ /speckit.plan（技术实现规划）-> /speckit.checklist（架构检查清单）→ /speckit.tasks（任务拆分）-> /speckit.analyze（影响分析）→ /speckit.implement（执行）→ /speckit.converge（收敛评估）
  • 三层定制体系：Extensions（新命令）→ Presets（模板覆盖）→ Bundles（角色包）
  • 4 层模板优先级：Project Override > Preset > Extension > Core
  • Python + uv 分发，支持 30+ agent 集成
  • MIT 协议

两条实用路径：

基础快速路径（适合快速实验）

/speckit.specify -> /speckit.plan -> /speckit.tasks -> /speckit.implement

完整生产路径（推荐用于正式功能）

/speckit.constitution -> /speckit.specify -> /speckit.clarify -> /speckit.plan -> /speckit.checklist -> /speckit.tasks -> /speckit.analyze -> /speckit.implement -> /speckit.converge

1.2 Trellis（Mindfold）

多平台 agent 工作流框架，给 agent 补"项目记忆 + 团队规范注入"能力。

  • 核心是 .trellis/ 目录：spec/（团队约定）、tasks/（PRD/任务状态）、workspace/（每人的会话日志）
  • 4 阶段循环：Plan（trellis-brainstorm）→ Implement（trellis-implement 子 Agent）→ Verify（trellis-check 子 Agent）→ Finish（trellis-update-spec 回写学习）
  • 跨 14 种 agent 平台共享同一套 spec
  • Node.js CLI 分发，AGPL-3.0

1.3 mattpocock/skills

不是流程框架，是一组独立的工程技能。 作者明确反对"接管流程"的做法：

"Approaches like GSD, BMAD, and Spec-Kit try to help by owning the process. But while doing so, they take away your control and make bugs in the process hard to resolve."

  • 小颗粒、可拆开用、可魔改
  • 区分 user-invoked（你主动敲命令，负责编排）和 model-invoked（agent 自己调用，负责具体实践）
  • 核心解决三个问题：对齐（grill-me）、共享语言（CONTEXT.md）、代码质量（tdd/code-review）
  • skills.sh 安装或 Claude Code plugin 订阅
  • ~60,000 newsletter 订阅者

第四部分：安装与更新

4.1 Spec-Kit

GitHub：https://github.com/github/spec-kit

协议：MIT

环境要求

  • Python 3.11+
  • uv（推荐）或 pipx
  • Git

安装

方式一：uv（推荐，从 GitHub 安装最新版）

uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@vX.Y.Z

将 vX.Y.Z 替换为 Releases 页面 上的最新版本号。

方式二：PyPI

uv tool install specify-cli

初始化项目

specify init my-project --integration copilot
cd my-project

初始化后，agent 中即可使用 /speckit.constitution、/speckit.specify、/speckit.plan、/speckit.tasks、/speckit.implement 等 slash 命令。

更新

# 检查是否有新版本（只读，不安装）
specify self check

# 预览升级内容（不实际安装）
specify self upgrade --dry-run

# 升级到最新稳定版
specify self upgrade

# 固定到指定版本
specify self upgrade --tag vX.Y.Z

扩展管理

specify extension search          # 搜索扩展
specify extension add <name>      # 安装扩展
specify preset search             # 搜索预设
specify preset add <name>        # 安装预设
specify bundle search             # 搜索角色包
specify bundle install <name>    # 安装角色包
specify bundle update             # 更新角色包

4.2 Trellis

GitHub：https://github.com/mindfold-ai/trellis

文档：https://docs.trytrellis.app

协议：AGPL-3.0

环境要求

  • Node.js ≥ 18
  • Python ≥ 3.9

安装

# 全局安装 Trellis CLI
npm install -g @mindfoldhq/trellis@latest

# 在项目中初始化（-u 指定你的用户名）
trellis init -u your-name

# 或指定目标平台初始化
trellis init --cursor --opencode --codex -u your-name

初始化后会在项目根目录生成 .trellis/ 目录，包含 spec/（团队约定）、tasks/（PRD/任务状态）、workspace/（会话日志）等子目录。

更新

Trellis 的更新涉及三个相互独立的版本，先理清它们各是什么：

  • ① npm 上的最新版本——发布到 registry 的最新稳定版
  • ② 本地 CLI 的版本——通过 trellis -v 查到、全局装在你机器上的那一份
  • ③ repo 里 trellis 的版本——随项目提交的 .trellis/ 配置与命令

两条命令各管一段升级链路，方向不能搞反：

# 把本地 CLI 升级到 npm 最新（② → ①）
trellis upgrade

# 把 repo 里的 .trellis/ 同步到与本地 CLI 一致（③ → ②）
trellis update --migrate

一次完整的升级通常是：先 trellis upgrade 更新本地 CLI，再进入项目目录执行 trellis update --migrate 把 repo 配置跟上。update --migrate 以本地 CLI 版本为基准，所以必须先升 CLI、再同步 repo，顺序反不了。

注意：upgrade 命令从 0.6 beta 起才有

本地 CLI 若仍是 0.5.x，执行 trellis upgrade 会报 unknown command 'upgrade'。先用 npm 手动把本地 CLI 升到 0.6+，之后就能正常用 trellis upgrade 了：

npm install -g @mindfoldhq/trellis@latest

这一步只动全局 CLI，.trellis/ 里的项目数据不受影响。

4.3 mattpocock/skills

GitHub：https://github.com/mattpocock/skills

环境要求

  • 无额外运行依赖（skills 是纯 Markdown 文件）
  • 需要 Claude Code、Codex 或其他支持 Agent Skills 标准的工具

安装

方式一：Claude Code 插件（推荐，自动更新）

# 在终端中
claude plugins install mattpocock-skills

# 或在 Claude Code 会话内
/plugin install mattpocock-skills

以只读插件形式安装，由 Claude Code 官方 marketplace 分发，自动更新。

方式二：skills.sh（可编辑副本）

npx skills@latest add mattpocock/skills

将 skill 文件复制到项目 .claude/skills/ 目录中，可以自由修改。安装过程中可以选择要包含哪些 skill。确保勾选 setup-matt-pocock-skills。

⚠️ 不要同时安装两种方式——否则每个 skill 都会出现两份，导致重复和混乱。选一种即可。

初始化

/setup-matt-pocock-skills

安装后每个仓库执行一次，用于配置 issue 追踪器（GitHub / Linear / 本地文件）、triage 标签和文档位置。

更新

  • 插件方式：更新自动推送，无需手动操作。
  • skills.sh 方式：执行 npx skills update 拉取最新版本。

第五部分：混合使用分析

4.1 分层模型

三个工具在不同层面工作：

┌─────────────────────────────────────────────────┐
│  第 1 层：需求对齐（"到底要做什么"）               │  ← mattpocock/skills 的 /grill-me 最强
├─────────────────────────────────────────────────┤
│  第 2 层：规格 & 计划（"怎么拆解"）               │  ← Spec-Kit 最强
├─────────────────────────────────────────────────┤
│  第 3 层：工程纪律（"怎么写好代码"）              │  ← mattpocock/skills 的 /tdd /code-review 最强
├─────────────────────────────────────────────────┤
│  第 4 层：跨会话记忆（"上次做到哪了"）            │  ← Trellis 最强
└─────────────────────────────────────────────────┘

4.2 兼容性判断

组合兼容度原因
Trellis + mattpocock/skills⭐⭐⭐ 最高目录不冲突（.trellis/ vs .claude/skills/）；Trellis 不锁死流程；mattpocock/skills 设计哲学就是"不拥有流程"
Spec-Kit + mattpocock/skills⭐⭐ 中等implement 阶段可内嵌 /tdd；但 CONTEXT.md 与 constitution.md 存在"谁当真相来源"的潜在摩擦，优化后可通过 constitution 显式声明解决（见方案 A）
Spec-Kit + Trellis⭐ 最低两者都控制任务来源、状态存储、session 上下文加载；tasks 目录冲突；slash command 入口冲突；上下文注入叠加爆炸

4.3 推荐混合方案

🥇 方案 A（优化版）：mattpocock/skills + Spec-Kit（最实用）

此方案将 grill-with-docs 置于需求澄清之后、技术计划之前，确保术语提炼基于已稳定的需求，避免返工。同时，在 constitution.md 中显式声明术语权威，彻底消除两套工具的摩擦。

阶段用谁具体命令与说明
① 定原则 Spec-Kit

/speckit.constitution

写入项目核心原则，必须包含以下术语权威条款（中英文均可）：

英文版：

## Terminology Authority Domain-specific terms used in this constitution and all downstream artifacts (specs, plans, tasks, code) follow the glossary in `CONTEXT.md`. When a term in `CONTEXT.md` conflicts with a principle stated here (e.g., the term's label obscures or contradicts a governed behavior), the principle governs. In that case, only the term's label in CONTEXT.md should be revised so it no longer conflicts — the underlying concept it refers to is not altered by this resolution. Until CONTEXT.md exists, this section is inactive; standard terminology in specs, plans, and tasks applies.

中文版：

## 术语权威 本 constitution 及所有下游产物（spec、plan、tasks、代码）中涉及的领域术语，以 `CONTEXT.md` 术语表为准。 当 `CONTEXT.md` 中的某个术语与本文件所述原则产生冲突时（例如：该术语的标签遮蔽或矛盾了某条受治理的行为），以原则为准。此时，仅需修订 `CONTEXT.md` 中该术语的标签，使其不再与原则冲突——该术语所指代的底层概念本身不因本次裁定而改变。 在 `CONTEXT.md` 尚未创建之前，本节不生效；spec、plan、tasks 中的术语按常规用法处理。
② 写需求 Spec-Kit /speckit.specify
用纯自然语言描述需求，不需要提前构思技术术语或模块名。
③ 消歧义 Spec-Kit /speckit.clarify
通过问答消除需求中的模糊点，确保"要做什么"完全锁定。
④ 建词典 👈 核心改动 mattpocock/skills /grill-with-docs
需求已明确，此时专门针对业务概念进行"术语烧烤"，产出 CONTEXT.md（统一词汇） + ADRs（架构决策）。
⑤ 做规划 Spec-Kit /speckit.plan
技术实现规划直接强制引用 CONTEXT.md 中的术语。文件名、模块划分必须与术语表一致。
⑥ 拆任务 Spec-Kit /speckit.tasks
任务中的文件路径、函数命名严格遵循 CONTEXT.md。
⑦ 写代码 Spec-Kit + Skills /speckit.implement
执行时，内部针对每个函数/模块使用 /tdd 红绿重构循环。
⑧ 守质量 mattpocock/skills /code-review
提交前最后一道闸，检查代码是否偏离了 CONTEXT.md 定义的统一语言。

为什么这个顺序是"黄金顺序"？

  • Spec-Kit 的 specify → clarify 解决了 "做什么（What）"。
  • grill-with-docs 紧接着解决了 "怎么称呼（Naming）"，且基于已稳定的需求，术语不会反复横跳。
  • 带着明确的命名去跑 plan，Agent 生成的架构图和模块关系清晰，不会出现"概念对不上代码"的割裂感。
  • constitution.md 中的显式声明让 Agent 在冲突时优先遵循 CONTEXT.md，彻底消除了两套工具的摩擦点。

【流程速览】

① 定原则 /speckit.constitution -> ② 写需求 /speckit.specify -> ③ 消歧义 /speckit.clarify -> ④ 建词典 /grill-with-docs -> ⑤ 做规划 /speckit.plan -> ⑥ 拆任务 /speckit.tasks -> ⑦ 写代码 /speckit.implement + /tdd -> ⑧ 守质量 /code-review

🥈 方案 B：mattpocock/skills + Trellis（长期迭代项目）

阶段用谁具体命令

计划 & 实现Trellistrellis-brainstorm → trellis-implement

为什么好？
Trellis 的 journals 是三者中唯一真正的跨会话记忆；mattpocock/skills 的 grilling + TDD 补上 Trellis 在需求对齐和测试纪律上的不足。

⚠️ 方案 C：三个全使用 —— 不推荐

问题说明

4.4 分层思路（核心原则）

主干流程选一个，具体执行技能从 mattpocock/skills 里挑单点嵌入。

  • 主干流程选一个：Spec-Kit（若你偏好强规格约束）或 Trellis（若团队多工具、需要并行开发）
  • 具体执行技能从 mattpocock/skills 里挑单点技能嵌进主干的某一步：
    • Spec-Kit 的 /speckit.clarify 后、/speckit.plan 前跑一次 /grill-with-docs 来建立术语表（方案 A 的精髓）
    • Spec-Kit/Trellis 的 implement 阶段内部用 /tdd 循环
    • 提交前用 /code-review（独立于两者之外，纯粹是最后一道质量闸）

这样规避的是"两套系统抢着当单一真相来源"的问题，同时吃到 mattpocock/skills 里"对齐+质量"这两个和流程框架本身不冲突的能力。

第六部分：可能的坑与摩擦点

坑 1：CONTEXT.md vs constitution.md 的职责边界（已通过方案 A 解决）

文档管什么类比
constitution.md决策原则（"我们怎么做选择"）宪法
spec.md需求定义（"我们要造什么"）产品需求文档
CONTEXT.md领域术语（"我们怎么称呼东西"）词汇表 / DDD 统一语言

传统摩擦：Agent 在 implement 阶段同时看到 constitution 里的"代码质量原则"和 CONTEXT.md 里的"命名规范"，如果两者对同一个概念用了不同措辞，Agent 会犹豫该用哪个词。

方案 A 的解法：在 constitution.md 中显式写入术语权威条款（见上文），声明 "领域术语以 CONTEXT.md 为准"，并规定当术语标签与原则冲突时如何裁决。这样 Agent 遇到冲突时有了明确的判断依据，无需猜测。

坑 2：Spec-Kit 的 TDD 排序 vs mattpocock/skills 的 /tdd 循环

  • Spec-Kit 的 tasks.md 会把测试任务排在实现任务前面（任务级排序）
  • mattpocock/skills 的 /tdd 是红-绿-重构循环（代码级循环）

两者不矛盾但粒度不同。如果让 Agent 自己判断"什么时候该用 TDD"，它可能在两个循环之间来回跳。

解法：在 constitution.md 或 tasks.md 里显式写："每个实现任务内部使用 red-green-refactor 循环"，把 /tdd 从"Agent 自主判断"变成"显式规则"。

坑 3：Spec-Kit + Trellis 的上下文注入叠加

  • Spec-Kit 在 implement 阶段注入 constitution.md + spec.md + plan.md + tasks.md
  • Trellis 在每个 session 启动时自动注入 .trellis/spec/ 下相关规格 + journals

两套系统同时往 prompt 里塞"项目规范"，token 预算被重复上下文吃掉，Agent 有效推理空间被压缩。

解法：不要同时使用。选一个做主干。

坑 4：任务管理重复

  • Spec-Kit：specs/001-xxx/tasks.md
  • Trellis：.trellis/tasks/（prd.md + implement.jsonl + check.jsonl）

同一个功能会同时存在于两套目录里，Agent 该听哪个 tasks 的顺序执行会产生歧义。

解法：只用一套任务管理。如果选 Spec-Kit 做主干，就不要同时用 Trellis 的 tasks。

坑 5：Slash command 入口冲突

  • Spec-Kit：/speckit.*
  • Trellis：/trellis:* 或 trellis-*

两者都想成为"入口"，叠加使用意义不大。

解法：选一个做主干，另一个只取单个功能（如只用 Trellis 的 journals 做记忆，不走它的完整命令链）。

第七部分：实操建议清单

✅ 该做的

  1. 只选一个"流程骨架"（Spec-Kit 或 Trellis），另一个只取单个功能。
  2. mattpocock/skills 永远可以叠加——它的设计哲学就是"不拥有流程"，和任何框架都不冲突。
  3. 统一术语——如果使用方案 A，务必在 constitution.md 中加入术语权威条款，并确保后续所有 Spec-Kit 产物都引用 CONTEXT.md。
  4. 显式声明规则——把"什么时候用 TDD""术语以谁为准"写进 constitution 或 spec，别让 Agent 自己猜。
  5. 定期跑架构改进——/improve-codebase-architecture 每隔几天跑一次，对抗 Agent 加速的软件熵增。

❌ 不该做的

  1. 不要同时跑两套任务管理。
  2. 不要让两个框架同时注入系统提示。
  3. 不要为了"全面"而全面——个人项目不需要 Bundles/Presets 体系。
  4. 不要把 mattpocock/skills 当流程框架用——它是调味料，不是主菜。
  5. 不要忽略 grilling——即使你用了 Spec-Kit 的 /speckit.specify，在 clarify 之后、plan 之前跑一次 /grill-with-docs 能大幅减少下游返工（方案 A 的核心）。

第八部分：一句话总结

工具一句话
Spec-Kit"先写清楚要什么，再让 AI 去造" —— 规格驱动的流程引擎
Trellis"让 AI 记住你的项目，按你的规矩办事" —— 带记忆的工程框架
mattpocock/skills"别让 AI 拥有流程，你拥有流程" —— 可组合的工程纪律工具箱

💡 核心结论

mattpocock/skills 是"调味料"，百搭不冲突；Spec-Kit 和 Trellis 是"主菜"，选一个做骨架。
最实用的组合是 mattpocock/skills（对齐 + 质量）+ Spec-Kit 或 Trellis（流程 + 记忆），而不是三个全上。
